# Learning-repo audit

A learning repo makes one promise to its reader: *what it says is true, and what it shows was
actually computed.* An audit finds out whether that promise holds and, where it doesn't, exactly
where. Readers can't easily check this themselves, which is why the audit has to.

The rubric is `references/rubric.md`. Read it before starting: it defines the nine criteria,
their anchors, the mechanical and sampled checks for each, the hard fails, the severity scale,
the repo profiles and the calibration. This file is the procedure.

## Ground rules

- **Measure, don't fix.** The audited repo is not modified, not even "obvious" one-line fixes.
  Fixing is a separate step (the `learning-repo-build` skill, in upgrade mode), done after the
  author has seen the report. That keeps the audit an honest measurement and leaves the author in
  control of their repo.
- **Work in a scratch clone.** Running figure scripts overwrites committed images, renders create
  output folders and installs create virtualenvs. Do all of that in
  `git clone --quiet <repo> <scratch>/<name>`, which also tests the build from a clean checkout
  instead of whatever is lying around in the working tree. If the working tree has uncommitted
  changes, say so in the report: the audit covers the committed state.
- **Evidence for every finding.** Each finding gives a `path:line` (or a URL) and either a quote,
  a command and its output, or the source that contradicts it. If you couldn't verify something,
  say "unverified" and why. Never guess.
- **Exhaustive where cheap, sampled where expensive, and say which.** Mechanical checks run on
  everything. Claim verification and figure re-runs are samples; the report states the sample size
  and how the sample was chosen, so the reader knows what "no problems found" covers.

## Workflow

1. **Orient (5 minutes).** Read the README, any CLAUDE.md / CONVENTIONS / ROADMAP / research log,
   the site config (`_quarto.yml` or similar) and the table of contents. Write down:
   - the repo's **profile** (book · notes · app · research; see the rubric);
   - its **thesis or purpose**, in one sentence;
   - its **target reader**;
   - its own stated standards (a conventions file is a promise; audit against it too).

2. **Run the mechanical checks.**
   ```bash
   python <skill-dir>/scripts/mechanical_checks.py <clone> --online
   ```
   The script lists missing and orphan images, referenced figures with no generating script,
   citation keys vs. the bibliography, entries with no identifier, arXiv ids that don't exist or
   whose title differs from the bib, unresolved DOIs, dangling paths in READMEs and project docs,
   broken internal links, and hygiene facts. Its output is a list of **candidates**. Open each
   one before calling it a finding: an "unscripted" image may be a labeled schematic or a logo,
   and a "dangling" path may be prose about something that deliberately doesn't exist.

3. **Build, test, render, deploy** from the clone, using the README's commands *verbatim* first.
   If they fail, record that (it's a finding), then do what's needed to continue. Typical steps:
   - `uv sync` or `pip install -e .`
   - the test suite
   - the linter, if configured
   - `quarto render docs`: record every warning
   - for a book that executes code at render: registering the repo's Jupyter kernel from
     the clone (`ipykernel install --name <name>`) overwrites the user's kernel of that
     name, which then points into a scratch directory that will be deleted. Either point
     the clone's `_quarto.yml` at a differently named kernel, or re-register the kernel
     from the original repo when you finish.
   - for an app, import every page headless (e.g. `streamlit.testing.v1.AppTest`)
   - `gh run list --limit 5` for CI on the default branch
   - for a book, compare the rendered chapter numbers (the `<title>` of each page in the
     rendered site) with the file-name numbering and the README's chapter count. A numbered
     index or map page shifts every chapter by one or two.
   - fetch the live site and compare it to the current build

   Count tests that check a numerical property against ground truth versus tests that only check
   that code runs. The script's "numeric-tolerance assertions" count is a first hint.

4. **Check the descriptions.** Compare the README, the GitHub description and topics
   (`gh repo view --json description,repositoryTopics,homepageUrl`), the site metadata, and the
   author's profile README if one lists the repo, against reality: counts of chapters, apps,
   figures and tests, and claimed features. Stale counts are cheap to find and erode trust.

5. **Verify a sample of claims (about 10 per repo).** Choose them deliberately:
   - (a) recent or frontier material, where a generating model's recall is weakest;
   - (b) specific numbers, defaults, hyperparameters, equations, dates and author lists;
   - (c) claims the argument rests on.

   For each one, open the primary source, give a verdict (ok · imprecise · wrong · not-found ·
   unreachable) and quote what the source actually says. For bibliography entries without
   identifiers, search for the paper and confirm it exists with that author list, year and venue.
   - Fetching PDFs: WebFetch often can't parse them. Download with `curl -sL` and use
     `pdftotext`.
   - arXiv's API rate-limits bursts: space requests by a few seconds.
   - A sibling repo's research log that records a source as opened and checked (e.g. the PDF
     text was quoted) is acceptable evidence. Cite the log, and say that's where it came from.

   Note also how each frontier claim is *framed*: dated? attributed? labeled as one paper's
   finding? That is criterion 6.

6. **Re-run figures (at least 3, always including the signature figure).**
   - In the clone, run the figure scripts. Then triage the differences with
     `python <skill-dir>/scripts/compare_figures.py <clone>`, using the figure environment's
     Python. Open both versions of any image that changed noticeably.
     - Differences from fonts, library versions or tight-bbox shifts change bytes, not content.
       They're a reproducibility note at most, not a finding.
     - Different numbers, curves or labels are findings.
   - Read the script: does it compute what the caption says, or plot hard-coded numbers?
   - Where the text claims typical behavior from a seeded run, re-run with one or two other
     seeds. An effect that appears on only some seeds isn't wrong, but presenting it as general
     is (criterion 3).
   - Check 3–5 numbers quoted in prose or captions against the fresh output.

7. **Read for pedagogy and economy.** Read two sections in full, one foundational and one
   advanced, as the target reader. Does each motivate, derive and connect? Is anything padded or
   repeated? Re-derive one key result yourself.

8. **Score last.** Use the anchors and the calibration in the rubric. Apply hard fails. Rank the
   findings by severity, and within a severity by how many readers each one misleads.

9. **Write the report** in the format below.
   - **Location:** unless the user names one, save it outside the audited repo, in a
     `learning-repo-audits/` directory next to it:
     `<parent-of-repo>/learning-repo-audits/<repo>-<YYYY-MM-DD>.md`. Don't save it in the
     session's working directory: that is often another repo. Give the user the path.
   - **Before saving, re-check every count and number in the report against the command output
     it came from.** Totals like "N of M entries" are easy to get wrong from memory, and a wrong
     count in an audit discredits the true findings around it. Show the user the verdict, the scores and the blockers
   in chat. The full report lives in the file.

Steps 5–7 are the expensive ones. For a quick screen, run steps 1–4 only and label the report
"mechanical screen, no claims sampled". Never present a screen as a full audit.

## Auditing several repos

If the question is which repo is more reliable, measured on equal terms (blinded copies,
planted errors, confirmed defects per 10,000 words), use the `learning-repo-compare` skill
instead: rubric scores drift between auditors and reward a visible paper trail.

Audit them one at a time with the same procedure and the same sample sizes, so the scores are
comparable. Then write `learning-repo-audits/summary-<date>.md`:
- a table with one row per repo: profile, the nine scores, hard fails and blocker count;
- the patterns that recur across repos (these usually point at the process or tool that made
  them, which is the most useful thing to fix);
- a recommended order for remediation.

If the user has authorized subagents, repos can be audited in parallel, one agent per repo, each
given this skill and the rubric. Otherwise run them sequentially.

Most repos have 3–10 findings that matter. Don't pad the list. Group repeated instances
("12 bibliography entries lack identifiers: …") into a single finding.

## Tone

Write the report the way you'd want your own work audited: blunt about substance, specific,
never snide. Credit what is good, by name, so it survives the revision. The author may have
written the repo with a weaker model and wants to know where it fell short. Make every finding
actionable.
